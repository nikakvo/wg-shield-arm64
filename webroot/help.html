1 · what this module does

WG Shield runs a WireGuard or AmneziaWG tunnel in the kernel, with no app. It starts at boot, survives killing apps from recents, follows Wi-Fi ↔ mobile switches by itself and has a kill switch: while a tunnel is on but not working, nothing leaves the phone around it.

Android does not see a VPN. There is no VPN key icon, apps see a normal network, and nothing depends on Android's VPN service - the tunnel is plain Linux routing below it. Calls over the mobile network (VoLTE, Wi-Fi calling), SMS and MMS keep using the carrier's own networks.

Tunnels come from the official WireGuard app (or an AmneziaWG config): export them there, import them here, then switch one on. Which kind a tunnel is, WG Shield sees by itself from the file (see 6).

needs
KernelWireGuard built in (CONFIG_WIREGUARD). The installer checks it and stops if it is missing. For AmneziaWG tunnels the kernel also needs AmneziaWG (CONFIG_AMNEZIAWG); without it only those tunnels cannot start, WireGuard tunnels work as usual.
Tunnelswg-quick format as the WireGuard app or a VPN provider exports them (a zip or single .conf files): one [Peer], AllowedIPs with 0.0.0.0/0, an Endpoint as an IPv4 address or a host name. An IPv6 address with ::/0 carries IPv6 too. Proton VPN's configs work as downloaded.
RootSukiSU Ultra, KernelSU, APatch or Magisk (WebUI through MMRL / KSU WebUI Standalone).
Tested on a Poco F6 Pro with Xiaomi.eu HyperOS 3 (Android 16) and an android13-5.15 GKI kernel. Other ROMs name and number their networks the same way (it is Android's own netd), but that is not tested.
2 · quick start
  1. Flash the zip, reboot.
  2. WireGuard app: ⋮ → Export tunnels. The zip lands in Download.
  3. This WebUI → Tunnels → Import from Download → Import. Then delete the file with ✕: it holds your private keys.
  4. Disconnect the tunnel in the WireGuard app - one key, one tunnel.
  5. Switch a tunnel on. The route at the top shows Phone → tunnel → Internet with a moving line within a few seconds.
  6. Dashboard → Exit → Check, or open DNS Test: the server's address shows, and your own DNS resolvers.

The manager's Action button turns the last used tunnel on or off without opening the WebUI.

3 · how it works
app on the phone
↓
routing rules (before Android's own)
↓
wgs0 - the kernel tunnel, encrypted
↓
your Wi-Fi or mobile network → VPN server → internet

The pieces

One interface, wgs0, always the same name whichever tunnel is on. A routing table (51820) that sends everything into it, with an unreachable route underneath: if the tunnel disappears, traffic has nowhere to go - it never falls back to your normal connection.

Routing rules with priorities 5000–5022 sit in front of Android's (which start at 10000):

rulewhat for
5000The tunnel's own encrypted packets to the server go out through your network.
5010–5013Local destinations stay local: your Wi-Fi LAN (router, printer, SSH from a laptop), hotspot devices, the local range of every other network.
5014Android's own network check and the hotel / airport login page stay on the network they are for.
5020Everything not bound to one network → the tunnel.
5021Everything bound to the current default network (Wi-Fi or mobile) → the tunnel.
5022Everything bound to another internet network → the tunnel.

Every network

Android keeps more than one network up: on Wi-Fi, mobile data usually stays connected in the background, and a new Wi-Fi is up for a few seconds before Android uses it. Apps and parts of Android can send traffic over such a network on purpose (Google's push service, for example, connects over a new Wi-Fi a split second after it appears). WG Shield sends that traffic through the tunnel too: a new network is caught the moment Android creates it.

Two things always go out on the network itself, never through the tunnel:

  • Android's network check (a request to connectivitycheck.gstatic.com/generate_204 and similar). Through the tunnel it would always succeed, and Android would take a broken Wi-Fi for a working one.
  • The login page of a hotel or airport Wi-Fi (Android's captive portal login). It can only open on that Wi-Fi.

Carrier service networks keep Android's routing - that is how IMS (VoLTE, Wi-Fi calling) and MMS keep working. Restricted networks (IMS and the like) are never touched; a network without internet (MMS only) is let go after one look at Android's network list. Dashboard → Tunnel → Other networks shows what goes where.

Watchdog

A background loop follows Android's network rules as they change: a new network goes through the tunnel within a fraction of a second, a new default network is followed at once. On top of that it checks every 10 seconds (every 2 seconds during the first minute after boot): the right tunnel is loaded, the server route follows the network, no rule is missing. Rules are changed without a gap - the new ones are in place before the old ones go - so the kill switch never opens. Anything off is put back and written to the log.

At boot

If a tunnel was on when the phone went down and the kill switch is on, a blocking rule is in place before Android starts its network. Nothing leaves the phone until the tunnel is up.

4 · states and the banner
statemeaning
protectedThe tunnel is up and answers.
connectingJust switched on, waiting for the first handshake (or for a network).
checkingAfter a restart or a switch the tunnel has a handshake again; WG Shield waits for an answer through it before it counts as fixed (a few seconds).
recoveringThe tunnel stopped answering and WG Shield is fixing it: a restart, or another tunnel of the same country (see 7). The banner says which step.
downNothing answers through the tunnel (or no handshake for more than 180 s) and self-healing could not fix it. Kill switch on: no internet. Off: direct connection until it answers again.
pausedYou paused it, or another VPN app is connected. Direct connection.
errorThe tunnel cannot be built (file gone, kernel refused it). Direct connection - the banner says why.
offNo tunnel switched on. Your normal connection, nothing installed.
A tunnel that stops answering is noticed within about 40 seconds, or 10 with Check every 5 s (see 7, Self-healing). WireGuard's own limit - no handshake for 180 s - stays as a second check.
5 · dashboard

Where the phone's traffic goes right now. Moving blue line: through the tunnel. Red cut: kill switch holds. Orange: straight to your connection.

Exit

Tunnel

The active tunnel, its type (WireGuard or AmneziaWG, with the kernel's AmneziaWG version), its server, the last handshake, data received and sent, and which network carries the tunnel. 6 · tunnels, countries, favorites, speed test, backup, import, amneziawg

Every imported tunnel is a row with a switch. One at a time: switching one on switches the other off; the interface stays wgs0, only keys, server and address change. All off = your normal connection.

Country boxes

Above the list, the tunnels are grouped in boxes: flag, country code and how many tunnels (🇧🇬 BG · 7). Tap a box to see only that country's tunnels; tap it again (or Show all) to see all of them. The page remembers the box you picked. A dot in the corner marks the box of the tunnel that is on: green and pulsing while it is protected, orange while it connects or is paused, red when it is down.

The country comes from the tunnel's name: the first part of exactly two capital letters between -, _ or . (wg-BG-14 → BG, wg-NL-FREE-3 → NL). Auto-switch uses the same rule for "the same country". Names without such a part (myhome, wg-pld) are in Others 🌐, the last box. Proton names the United Kingdom UK: the box keeps that label and shows the British flag.

Inside a box the tunnels are sorted by number (BG-14 before BG-100). The tunnel that is on always stays at the top of the list, whatever box is picked.

Favorites

The ☆ on a row marks a tunnel as a favorite (★). All favorites are in the Favorites box, the first one; it appears when there is at least one. Deleting a tunnel also removes its star; importing it again with the same name keeps it.

WireGuard / AmneziaWG filter

When both kinds of tunnels are imported, All · WireGuard · AmneziaWG above the boxes shows only one kind; the boxes and their numbers follow it.

Speed test

Pick a box and tap Test. WG Shield measures every server address in the box once: how long the first handshake takes ("connects in") and the average of 3 pings through the tunnel to 1.1.1.1. A line shows which server is being tested; it takes a few seconds per address. Nothing is switched: the rows are then grouped by server address, the fastest first and marked, and you pick. Every row shows its time, and each group says how old its result is.

Why per address: a VPN provider runs several "servers" on one machine. With Proton, BG-14, BG-18, BG-20 and BG-24 can all connect to the same address (the Server on the Dashboard) and leave through different exit addresses (the Internet address). They are as fast as each other and they usually fail together, so one measurement counts for the whole group. They are not duplicates - a different exit address can help when a site blocks one - but for a backup, keep tunnels on different server addresses.

How it measures without touching your connection: each address gets a second, temporary tunnel interface next to the running one, with one tunnel of that address; only the test's own packets use it, and it is removed right after (also if the test is stopped). The tunnel that is on keeps running and the kill switch keeps working; the address of the tunnel that is on is measured through it (ping only). A tunnel with the same key as the one that is on is never loaded twice (the server would drop one of them); another tunnel of that address is used, or the group says it was not tested.

Results: no handshake = the server did not answer at all; no answer through it = it connected but carried nothing. Results are kept (also after a reboot) until the next test of that box, and Auto-switch uses them (section 7).

Clear all

Clear all, at the right above the boxes, deletes every imported tunnel at once (with their keys and stars) instead of one ✕ at a time - for example before importing a fresh export. Tap it twice to confirm. The tunnel that was on turns off: your normal connection, no kill switch, until you import and switch one on again. Speed test results are kept.

Backup and restore

The Backup section saves every imported tunnel, and which ones have a star, to /storage/emulated/0/wg-shield/wg-shield-backup.zip: the same kind of zip the WireGuard app exports, one .conf per tunnel, plus favorites.txt and backup-info.txt. The WireGuard / AmneziaWG app can import it too, and so can Import from Download here. There is one backup: Backup again replaces it (tap twice when one exists). The new zip is written next to the old one, unpacked again and compared file by file, and only then put in its place - if anything fails, the old backup is still there.

The backup stays when you remove or reinstall the module, and after Clear all. Restore (tap twice) imports every tunnel of the backup and gives the backed-up favorites their star again; a tunnel with the same name is replaced, tunnels that are not in the backup stay. The tunnel that is on is not changed. ✕ (tap twice) deletes the backup.

To keep it somewhere else, copy the zip to your computer. The files hold your private keys, like an export in Download: apps with access to all files can read them.

Import

Import reads the WireGuard app's export zip, or single .conf files, from Download. Files that do not fit (several peers, no full tunnel, an IPv6 endpoint) are skipped and the Log says why. Importing a tunnel with a name that already exists replaces it. Names keep letters, digits, . _ -; other characters become _.

From a file the module uses only the WireGuard keys and addresses. DNS is ignored (DNS is left to the system or DNSCrypt Proxy), as are PostUp, Table and the like. A tunnel without PersistentKeepalive gets 25 s, so the health check always has fresh handshakes.

Private keys are stored in /data/adb/wg-shield/tunnels/, readable only by root. They never appear in the WebUI, the log, the status or the Report. The export in Download is readable by apps - delete it after importing.

AmneziaWG

AmneziaWG is WireGuard with extra settings that make the traffic harder to recognise and block. A file with any AmneziaWG setting (Jc, Jmin, Jmax, S1-S4, H1-H4, I1-I5, HeaderProtectionKey, ContentPaddingAddition, RandomTrailers and the like) is an AmneziaWG tunnel; any other file is plain WireGuard. Nothing to choose: the tunnel row shows an AWG badge and Dashboard → Tunnel → Type says which one runs.

Both kinds use the same interface (wgs0), the same routing, kill switch and pause, and work the same way with DNSCrypt Proxy and VPN Hotspot. Switching between a WireGuard and an AmneziaWG tunnel creates wgs0 again with the other type; the kill switch holds meanwhile.

The AmneziaWG settings are passed to the kernel unchanged, checked by the awg tool. If it refuses one, the tunnel shows error and the Log names the setting. HeaderProtectionKey is a secret like the private key and is never shown.

Without AmneziaWG in the kernel, AmneziaWG tunnels can still be imported, but their switch is greyed out and the row says AmneziaWG is not in this kernel.
7 · kill switch, self-healing and pause

Kill switch

On (default): while a tunnel is switched on but not working, the phone has no internet at all. Off: the phone uses your connection directly while the tunnel is down, and goes back into the tunnel by itself when it answers again.

The kill switch never blocks when you turn the tunnel off, pause it, or when it cannot be built at all (error).

Self-healing

Every 30 seconds (or every 5 seconds, see Check every below; with the Battery profile only while the screen is on) WG Shield sends one ping through the tunnel (to 1.1.1.1, then 9.9.9.9 - never around it). Only an answer counts: traffic coming in alone does not prove that the way out works. No answer to two tries = the tunnel does not work, noticed within about 40 seconds (10 seconds with 5 s). A server that never answers a ping (some home servers drop it) is not called dead for that - for such a tunnel WireGuard's own 3-minute rule decides. While the phone has a network, WG Shield then fixes it without waiting for you:

  1. Two restarts (always on). The tunnel is built again, which makes a fresh handshake from a new port and looks a host-name server up again. This fixes a router that was restarted, a lost connection, a server that hung for a moment. Each step gets 10 seconds; it counts as fixed only when an answer comes back through the tunnel, not just a handshake.
  2. Auto-switch on failure (Settings, off by default). If the restarts did not help, WG Shield tries your other tunnels, at most 5: first the same country - the two capital letters in the name, so wg-BG-14 is followed by the other *-BG-* tunnels - then any other tunnel (another country, a home server). A tunnel on a server address that already failed in this attempt is never tried (tunnels on one address usually fail together). Inside each group the last speed test decides: the fastest address first, untested ones next, ones that failed the test last. The first one that answers stays on, and the Tunnels tab shows it switched on.
  3. Nothing helped: WG Shield goes back to the tunnel you picked and it stays down - with the kill switch on, no internet. It keeps checking that tunnel quietly (every 15 seconds, every 30 with Check every 30 s) and is back the moment it answers; a new attempt starts when the network changes.

The kill switch holds during every step - nothing leaves the phone outside the tunnel. Switching a tunnel yourself, pausing or turning it off stops an attempt at once.

A typical case for auto-switch: the same tunnel file (the same key) used on two devices at once. The server answers only one of them, so restarts cannot help, but another tunnel can. Give every device its own config.

Check every: 5 s, 30 s or Off

Settings → Check every decides how often the ping above is sent:

  • 30 s (default) - 120 pings an hour, about 35 KB. A dead tunnel is found in about 40 seconds.
  • 5 s - 720 pings an hour, about 200 KB. A dead tunnel is found in about 10 seconds. While the phone is otherwise idle on mobile data, the frequent pings keep the modem awake, which costs some battery.
  • Off - no pings at all. Only WireGuard itself watches the tunnel (no handshake for 3 minutes = down), which sends nothing extra. The self-healing and the notification still work, they just start later. Battery / Always has no effect then.

A ping is tiny, and it goes through the tunnel: the resolver it is sent to sees the VPN server's address, not yours. A recovery that has started checks every few seconds, whatever is set here, so its steps can tell at once whether they worked. A network change checks at once too.

Checks: Battery or Always

Settings → Checks decides when the pings are sent:

  • Battery (default) - only while the screen is on. With the screen off nothing is pinged: no wake-ups, no data, the phone can sleep. The first check runs the moment the screen comes on, so a tunnel that died in your pocket is fixed within seconds of picking up the phone. While the screen is off, WireGuard's own limit (no handshake for 3 minutes) still notices a dead tunnel and starts the same recovery.
  • Always - day and night, also with the screen off. For devices on your hotspot, or apps that must stay connected in the background. Costs a little battery while the phone is idle.

A recovery that has started is always followed to the end, screen on or off.

Notification

One notification (Settings → Notification, on by default) when WG Shield had to switch to another tunnel, or when nothing helped - it says what was tried, so you learn that you have no internet without opening the manager. A restart that fixed the tunnel shows nothing (it is in the Log). When the tunnel answers again after a failure, the notification is replaced with that news. Send a test notification shows how it looks.

It is posted through Android's shell (it appears as Shell / Command line in the notification shade), so no extra app is needed.

Pause

15 minutes, 1 hour or 4 hours on your normal connection, then the tunnel comes back. Resume now ends it early. A reboot ends a pause.

Another VPN app

While any VPN app is connected (WireGuard, Proton VPN, v2rayNG…) WG Shield steps aside and shows paused. It comes back when that VPN disconnects. That way the app stays a fallback, and two tunnels never fight over one key.

8 · with the other modules of the set
app DNS → DNSCrypt Proxy on the phone → tunnel → encrypted resolvers
app traffic → ipset blocklists → tunnel

DNSCrypt Proxy

WG Shield never sets DNS. DNSCrypt Proxy keeps answering every DNS query on the phone; its own connections to the resolvers simply go through the tunnel. Its IP mode decides whether the phone has IPv6 at all (see 9).

ipset

Its lists apply as always. A tunnel server must never be listed, or the tunnel cannot connect: check the server's address with ipset's Check tool, and add it to its allowlist if needed.

VPN Hotspot

VPN Hotspot (1.0-r13 or newer) reads WG Shield's status and sends hotspot devices through the same tunnel whenever it is up. Switching the server here needs nothing there. When you turn WG Shield off or pause it, hotspot devices go direct like the phone. While the tunnel connects or is down, they follow VPN Hotspot's own kill switch (no internet when it is on). Older versions of VPN Hotspot only follow Android's VPN and do not see WG Shield.

LAN Cloak

The Dashboard only shows its state: LAN Cloak hides what the Wi-Fi network itself sees of the phone (no device name in DHCP, no mDNS / SSDP / LLMNR announcements), the tunnel covers everything else, and neither module changes anything in the other.

9 · ipv6 and other limits
  • IPv6. A tunnel with an IPv6 address and AllowedIPs containing ::/0 carries IPv6 too (Dashboard → IPv6: through the tunnel). A tunnel without it blocks the phone's IPv6 while it is on (unreachable), so nothing goes around it - apps switch to IPv4 at once. DNSCrypt Proxy's ipv4 mode keeps IPv6 off for the whole phone; then every tunnel carries IPv4 only. Switch it to dual and the tunnel picks IPv6 up by itself within seconds.
  • The server is reached over IPv4. Proton's commented-out IPv6 Endpoint line is only another way to reach the server, not needed for IPv6 inside the tunnel - leave it commented.
  • One peer, full tunnel. Split tunnels and several peers are not supported.
  • Host-name endpoints (e.g. a home server on dynamic DNS) are looked up when the tunnel starts, with one plain DNS query to Quad9 sent outside the tunnel - before the tunnel is up there is no other way. If such a tunnel stops answering, the name is looked up again (at most once a minute), so an address change at home is followed by itself. IPv6 endpoints are not supported.
  • Same LAN on both sides. Addresses of your own Wi-Fi network always stay local. If a home VPN uses the same range as your Wi-Fi (both 192.168.1.x), devices behind that VPN cannot be reached while you are on that Wi-Fi.
  • No per-app bypass. Everything the phone sends goes through the tunnel, except carrier services (IMS, MMS), Android's network check and the captive portal login page (see 3).
  • What the network still sees. Android's network check runs on each new network (a request to Google's generate_204); a VPN cannot hide it without breaking Wi-Fi detection. What the router sees on the local network (DHCP host name, device announcements) is outside a VPN's reach.
  • Hotspot devices are routed by VPN Hotspot, not by WG Shield (see 8); they get IPv4 only.
10 · command line

Every WebUI action is a ctl.sh command. From Termux:

su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh status'   # state, tunnel, handshake
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh list'   # imported tunnels
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh import <zip|conf>'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh up [name]'   # last used when no name
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh switch <name>'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh down'   # normal connection
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh pause <minutes>'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh resume'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh set killswitch 0|1'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh set autoswitch 0|1'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh set notify 0|1'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh set profile battery|always'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh set checks 5|30|off'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh restart'   # watchdog + tunnel again
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh notifytest'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh remove <name>'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh removeall'   # delete every imported tunnel; the tunnel turns off
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh backup'   # save all tunnels to /storage/emulated/0/wg-shield/wg-shield-backup.zip (replaces the old one)
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh restore'   # import the tunnels of the backup
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh backupinfo'   # is there a backup, how many tunnels, when
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh delbackup'   # delete the backup
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh test BG'   # speed test of a box: country code, others or favorites
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh fav add <name>'   # favorite (☆ → ★); fav del <name> removes it
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh log [lines|clear]'
su -c '/system/bin/sh /data/adb/modules/wg-shield/ctl.sh diag'   # report, no keys

The wg tool is on the path too: su -c '/system/bin/wg show wgs0' (private key hidden). For an AmneziaWG tunnel use awg: su -c '/system/bin/awg show wgs0'. That output shows the header protection key, so do not share it - the Report hides it.

11 · troubleshooting

No internet

State down? The server does not answer, the restarts (and auto-switch, if on) did not help, and the kill switch holds. Switch to another tunnel, or pause. Stays connecting? Check the server is not blocked by ipset (see 8), then send the Report.

Something looks stuck

The Dashboard does not change, the watchdog shows stopped, or the tunnel does not come back after the network returned: Settings → Maintenance → Restart WG Shield (tap twice). It stops the watchdog, builds the tunnel again with a new connection to the server and starts the watchdog again, in a few seconds and without a reboot. Your tunnel, settings, a pause or "off" stay as they are; the kill switch keeps blocking while it restarts. If it does not help, send the Report.

Paused and I did not pause it

A VPN app is connected - the banner names it. Disconnect it.

Import skipped a tunnel

The Log names the file and the reason: a key that is not a real key (for example one replaced by *****), several peers, not a full tunnel, a bad endpoint.

"Rules changed by someone else - repaired"

Something removed one of the module's routing rules; the watchdog put it back. Once is harmless. If it repeats every few seconds, another module fights over the same rules - send the Report.

"Rules check: IPv4 x of y"

After changing its rules, the module counts them; this line means the kernel holds a different number than wanted, and lists both. The next change of network sets them again. If it repeats, send the Report.

Something is wrong and I need internet now

Action button in the manager (off), or ctl.sh down. If the module itself misbehaves: disable it in the manager and reboot - nothing of it stays active.

AmneziaWG tunnel shows an error

this kernel has no AmneziaWG: the kernel lacks CONFIG_AMNEZIAWG - use a WireGuard tunnel or a kernel with AmneziaWG. AmneziaWG settings were refused: the Log names the setting; the file may be for a newer AmneziaWG version than this module's awg tool.

No notification

Tap Send a test notification in Settings. If nothing appears, the notifications of the system app Shell (on Xiaomi: Command line) are switched off: Settings → Notifications → that app. The Log says notification could not be shown when Android refused it.

Watchdog not running

Reboot. If it stays stopped, the Log says why.
